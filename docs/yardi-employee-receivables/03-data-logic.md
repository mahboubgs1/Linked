# 03 — منطق البيانات وجداول Yardi المعنية

هذه الوثيقة تحدد: من أين تأتي كل قيمة، كيف تُحسب، وكيف نثبت صحتها.

---

## 1. جداول Yardi المعنية ومستوى اليقين

> ⚠️ **قاعدة العمل:** أسماء الجداول والأعمدة أدناه هي **نقطة انطلاق للتحقق**، وليست حقيقة
> مسلّمة. تختلف بين إصدارات Voyager وبين إعدادات العملاء. كل عنصر مصنّف بدرجة يقين، وكل
> عنصر بدرجة "يجب التحقق" يُثبَّت في `EMPRCV_SchemaMap` قبل كتابة أي مشهد.

### 1.1 الكائنات الأساسية

| الكيان المنطقي | جدول Yardi المتوقع | الغرض في الحل | درجة اليقين |
| -------------- | ------------------ | ------------- | ----------- |
| حركات الأستاذ العام | `gltrans` | مصدر كل المبالغ والتواريخ | عالية (الاسم) / **يجب التحقق** (الأعمدة) |
| رؤوس المستندات | `header` | نوع المستند، رقمه، حالته، تاريخه | عالية (الاسم) / **يجب التحقق** (الأعمدة) |
| دليل الحسابات | `account` | رقم/اسم/نوع الحساب، أساس السيجمنتيشن | عالية |
| الكيان / العقار | `property` | الكيان المحاسبي، العملة، السنة المالية | **يجب التحقق** (قد يكون `entity`/`owner` حسب الإعداد) |
| الموردون | `vendor` | تمثيل الموظف عند مصدر `VENDOR` | عالية |
| الدفاتر | `book` | فصل دفتر الاستحقاق عن غيره | **يجب التحقق** |
| الفترات المحاسبية | جدول الفترات / تقويم Voyager | ربط تاريخ الترحيل بالفترة | **يجب التحقق** |
| شجرة الحسابات | جدول الشجرة/الكتاب | نطاق الحسابات بنمط `TREE` | **يجب التحقق** |
| أمان المستخدم | جداول أمان Voyager | نطاق الكيانات المسموح بها | **يجب التحقق** (يختلف جوهرياً بين الإصدارات) |
| بيانات الموظف (HR) | وحدة HR إن كانت مفعّلة | القسم، المسمى، تواريخ الخدمة | **يجب التحقق** (قد تكون غير مفعّلة) |

### 1.2 الأعمدة المطلوبة منطقياً (بغض النظر عن اسمها الفعلي)

| العمود المنطقي | ما نحتاجه منه | مرشّحات الاسم في Yardi |
| -------------- | ------------- | ---------------------- |
| `TransId` | مفتاح فريد للسطر | `hMy` |
| `EntityId` | مفتاح الكيان في السطر | `hProp` |
| `AccountId` | مفتاح الحساب | `hAcct` |
| `HeaderId` | مفتاح الرأس | `hHead` / `hHeader` |
| `PostDate` | تاريخ الترحيل | `dPost` |
| `Amount` | المبلغ بإشارة (مدين موجب) | عمود المبلغ في `gltrans` — **يجب التحقق من الاسم والدقة** |
| `BookId` | الدفتر | `hBook` |
| `DocType` | نوع المستند | عمود النوع في `header` |
| `Status` | حالة الترحيل | عمود الحالة في `header` |
| `AccountCode` | رقم الحساب المعروض | `sAcctCode` أو ما يعادله |

> **بروتوكول التحقق:** لكل عمود أعلاه، ينفّذ فريق قاعدة البيانات
> `SELECT TOP 20 * FROM <table>` + مقارنة ناتج تجميعي مع تقرير Voyager قياسي معروف
> (ميزان مراجعة لحساب واحد وفترة واحدة). لا يُعتمد الاسم بالاستنتاج من التسمية وحدها.

### 1.3 خريطة السكيما (`EMPRCV_SchemaMap`)

```
LogicalObject   LogicalColumn   PhysicalTable   PhysicalColumn   Verified   VerifiedBy   VerifiedOn
GLTrans         TransId         gltrans         hMy              1          DBA          2026-09-01
GLTrans         Amount          gltrans         <TBD>            0
Header          DocType         header          <TBD>            0
...
```

مشاهد `vw_Src_*` تُولَّد يدوياً مرة واحدة بعد اكتمال هذا الجدول (وليس ديناميكياً عبر
SQL نصّي — تجنّباً لمخاطر الحقن وضعف خطط التنفيذ).

## 2. منطق نسبة الحركة إلى موظف (Employee Resolution)

يُطبَّق بالترتيب حسب `EMPRCV_EmployeeSource.Priority` وأول تطابق يفوز:

```
1) MANUAL   : وجود سطر في EMPRCV_ManualMap لهذه الحركة        → EmployeeKey منه
2) VENDOR   : header.VendorId موجود ومصنّف كموظف               → عبر vw_Src_Vendor
3) SEGMENT  : شريحة "الموظف" في رقم الحساب (SegEmployeeNo)     → عبر vw_Segment
4) SUBACCT  : الحساب نفسه مرتبط بموظف في EMPRCV_ManualMap/الإعداد
5) REF      : استخراج رقم الموظف من المرجع/الوصف بنمط منضبط
6) وإلا      : EmployeeKey = -1  (#UNMAPPED)
```

قواعد صارمة:

- **لا تخمين:** نمط `REF` يقبل فقط نمطاً محدداً مسبقاً (مثال: `EMP-#####`) وبتطابق تام،
  ولا يُستخدم البحث الجزئي غير المنضبط.
- **لا حذف:** الحركة غير المنسوبة تبقى في الإجماليات تحت `#UNMAPPED`، لأن حذفها يكسر
  ضابط المطابقة AC1 ويخفي مشكلة بيانات حقيقية.
- **الثبات التاريخي:** التغيير في الخريطة اليدوية يُسجَّل بتاريخ، ولا يُعاد كتابة اللقطات
  المجمّدة الصادرة سابقاً.

## 3. منطق نطاق الحسابات

```
حركة تدخل النطاق  ⇔  ∃ سطر في EMPRCV_AccountScope حيث:
        (ScopeType = 'LIST'  AND AccountId ∈ القائمة)
     OR (ScopeType = 'RANGE' AND AccountCode BETWEEN From AND To)
     OR (ScopeType = 'TREE'  AND AccountId ضمن أبناء العقدة)
  AND (EntityId = حركة.EntityId  OR  EntityId IS NULL)   -- NULL = كل الكيانات
  AND حركة.PostDate BETWEEN EffFrom AND EffTo             -- سريان التعريف
```

الفئة (`Category`) تُشتق من سطر النطاق المطابق، فتغيير تصنيف حساب لاحقاً لا يغيّر تصنيف
الحركات التاريخية — شرط أساسي لثبات التقارير المقارنة.

**حالة التداخل:** إذا طابقت حركةٌ أكثرَ من سطر نطاق، يُختار الأكثر تحديداً
(`LIST` > `RANGE` > `TREE`، ثم الكيان المحدد قبل `NULL`). التداخل يُبلَّغ في تقرير
فحص الإعداد `usp_Config_Validate` كتحذير.

## 4. حساب الأرصدة

### 4.1 الرصيد حتى تاريخ (As-of Balance)

```
Balance(emp, entity, asOf) = Σ Amount
  WHERE EmployeeKey = emp AND EntityId = entity
    AND PostDate <= asOf
    AND ضمن نطاق الحسابات والدفتر والحالة المرحّلة
```

- الإشارة: مدين موجب. الرصيد الموجب = الموظف مدين للشركة.
- **مهم:** الفلترة على **تاريخ الترحيل** لا تاريخ المستند. الفلترة على تاريخ المستند تنتج
  أرصدة لا تطابق ميزان المراجعة أبداً — وهو أشيع خطأ في هذا النوع من التقارير.

### 4.2 الرصيد الافتتاحي وحركة الفترة (R2)

```
Opening(emp, from)   = Σ Amount WHERE PostDate <  from
PeriodDebit          = Σ Amount WHERE PostDate BETWEEN from AND to AND Amount > 0
PeriodCredit         = Σ |Amount| WHERE PostDate BETWEEN from AND to AND Amount < 0
Closing              = Opening + PeriodDebit − PeriodCredit
```

### 4.3 الرصيد المتحرك (Running Balance)

```sql
Opening
+ SUM(Amount) OVER (
      PARTITION BY EntityId, EmployeeKey
      ORDER BY PostDate, HeaderId, TransId          -- ترتيب حتمي
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS RunningBalance
```

الترتيب الحتمي (`PostDate, HeaderId, TransId`) إلزامي: أي ترتيب غير فريد ينتج كشفاً
مختلفاً عند كل تشغيل، وهو أمر غير مقبول تدقيقياً.

## 5. منطق الأعمار (Aging)

### 5.1 الوضع الافتراضي: FIFO (الأقدم يُسدَّد أولاً)

بما أن المصدر هو GL (لا يوجد تطبيق مباشر بين مدين ودائن)، نطبّق مطابقة FIFO حسابية:

```
لكل (موظف، كيان):
  TotalCredit = Σ |Amount| للحركات الدائنة حتى تاريخ الرصيد
  للحركات المدينة مرتّبة تصاعدياً بتاريخ الترحيل:
      CumDebit_i   = Σ Debit حتى الحركة i (تراكمي)
      Unpaid_i     = MIN( Debit_i , MAX(0, CumDebit_i − TotalCredit) )
  الرصيد = Σ Unpaid_i        (= الرصيد الحسابي نفسه عندما يكون موجباً)
  العمر  = DATEDIFF(day, PostDate_i, AsOfDate)  لكل جزء غير مسدَّد
```

خصائص هذه الطريقة:

- قابلة للتنفيذ بمجموعة واحدة (Window Functions) بلا مؤشرات — أداء ممتاز.
- مجموع شرائح الأعمار = الرصيد الإجمالي دائماً (معيار القبول AT3).
- إذا تجاوز الدائن المدين (رصيد دائن)، تكون كل الأجزاء مسدَّدة والفائض يظهر في عمود
  **"دائن غير مطبَّق"** ولا يدخل شرائح الأعمار.

### 5.2 الوضع البديل: تاريخ الحركة (`TRANDATE`)

كل حركة (مدينة أو دائنة) تُبوَّب بعمرها الخاص. أبسط وأسرع، لكنه قد يُظهر أرصدة سالبة داخل
شرائح — يُستخدم فقط عند طلب صريح من المالية.

### 5.3 شرائح الأعمار

من `EMPRCV_AgingBucket` (افتراضياً 0–30 / 31–60 / 61–90 / 91–180 / >180). تغيير الشرائح
= تعديل بيانات، لا إعادة نشر تقرير.

## 6. السيجمنتيشن

### 6.1 التفكيك

```
POSITION : Seg_n = SUBSTRING(AccountCode, StartPos_n, Length_n)
DELIMITER: Seg_n = العنصر رقم n بعد التقسيم على الفاصل المعرَّف
TABLE    : Seg_n = ربط بجدول الشرائح في Voyager (إن وُجد)
```

كل شريحة في `EMPRCV_SegmentDef`: الرقم، التسمية (عربي/إنجليزي)، الوضع، الموضع/الطول،
جدول القيم المسموحة، هل تُستخدم كفلتر، هل تُعرض كعمود، وهل هي شريحة "الموظف" أو "القسم".

### 6.2 الفلترة

فلاتر الشرائح تُطبَّق على **الحساب** لا على الحركة، لذا تُدفع إلى داخل `vw_AccountScope`
قدر الإمكان (تقليل حجم الحركات المقروءة — راجع `05-...` §1).

### 6.3 التوسّع

إضافة شريحة سادسة مستقبلاً = سطر في `EMPRCV_SegmentDef` + عمود إضافي في المشهد + عمود
مخفي جاهز في الـ RDL. لذلك تُصمَّم التقارير بـ **6 أعمدة شرائح** من البداية (الخامسة
والسادسة مخفيتان افتراضياً) — توسعة بلا إعادة تصميم.

## 7. تعدد الشركات والكيانات

| البند | القرار |
| ----- | ------ |
| مستوى التجميع | الكيان هو المستوى الذري؛ الشركة تجميع أعلى من `vw_Src_Entity.CompanyId` |
| موظف في عدة كيانات | صف لكل (موظف، كيان) في R1، وكشف منفصل لكل كيان في R2 |
| رصيد الموظف الموحّد | صف تجميعي اختياري "إجمالي الموظف عبر الكيانات" بشرط وحدة العملة |
| العملة | لا يُجمع مبلغان بعملتين مختلفتين إطلاقاً؛ إما تجميع منفصل أو تحويل صريح |
| التحويل (اختياري) | بسعر تاريخ الرصيد من جدول أسعار الصرف، مع إظهار السعر المستخدم في التذييل |
| الأمان | تقاطع إلزامي بين الكيانات المطلوبة ونطاق صلاحية المستخدم قبل أي قراءة |

## 8. حقول نموذج الاعتماد (R3) ومصادرها

| الحقل | المصدر |
| ----- | ------ |
| اسم الشركة/الكيان + الشعار | `vw_Src_Entity` + إعداد الشعار |
| رقم المرجع | `EMPRCV-C-{EntityCode}-{FY}-{EmpCode}-{Seq}` من `EMPRCV_ConfirmationLog` |
| بيانات الموظف | `vw_Employee` |
| تاريخ نهاية السنة | معامل `@FYEndDate` (افتراضي من `vw_Src_Entity.FiscalYearEnd`) |
| الرصيد النهائي | `EMPRCV_BalanceSnapshot` (اللقطة المجمّدة) |
| تفصيل الفئات والأعمار | نفس اللقطة |
| نص الإقرار | `EMPRCV_DeclarationText` (اللغة + الإصدار المعتمد) |
| خانات التوقيع والاعتمادات | معامل `@Approvals` |
| بيانات الإصدار | المستخدم + التاريخ/الوقت + وضع الإصدار |

### 8.1 اللقطة المجمّدة (Snapshot)

```
usp_Snapshot_Freeze(@EntityIds, @FYEndDate, @UserId)
  → يكتب صفاً لكل (كيان، موظف) في EMPRCV_BalanceSnapshot:
      SnapshotId, FrozenOn, FrozenBy, Balance, ByCategory, ByAging,
      SourceRowCount, SourceChecksum
```

`SourceChecksum` = بصمة تجميعية للحركات الداخلة في اللقطة. عند إعادة التشغيل لاحقاً،
تُقارن البصمة الحالية بالمجمّدة: أي اختلاف يعني قيوداً بأثر رجعي بعد الإصدار، فيظهر تنبيه
صريح ويُدرج في تقرير الفروقات للمدقق — بدل اكتشاف الفرق أثناء التدقيق.

## 9. ضوابط المطابقة (Reconciliation Controls)

| # | الضابط | المعادلة | التكرار |
| - | ------ | -------- | ------- |
| RC1 | مجموع الموظفين = ميزان المراجعة | `Σ Balance(all emp) = Σ GL(scope accounts, asOf)` | كل تشغيل لـ R1 |
| RC2 | الأعمار = الرصيد | `Σ Buckets = Balance` لكل موظف | كل تشغيل |
| RC3 | R2 = R1 | `Closing(R2) = Balance(R1)` لنفس الموظف والتاريخ | كل تشغيل لـ R2 |
| RC4 | R3 = اللقطة | `Form.Balance = Snapshot.Balance` | كل إصدار |
| RC5 | اكتمال النسبة | `Count(#UNMAPPED) = 0` | يومي (منبّه) |
| RC6 | ثبات اللقطة | `Checksum(now) = Checksum(frozen)` | عند إعادة إصدار R3 |

الضوابط RC1، RC2، RC5 تُنفَّذ أيضاً كوظيفة مجدولة ليلية ترسل تنبيهاً عند أي انحراف —
لا تنتظر أن يكتشف المدقق الخطأ.

## 10. جودة البيانات — فحوصات ما قبل الإطلاق

| # | الفحص | الإجراء عند الفشل |
| - | ----- | ----------------- |
| DQ1 | حركات في نطاق الحسابات بلا موظف | تنقية بيانات + خريطة يدوية قبل الإطلاق |
| DQ2 | موردون مصنّفون كموظفين بلا رقم موظف | تصحيح البيانات في Voyager |
| DQ3 | أرقام موظفين مكررة عبر المصادر | توحيد + قاعدة أولوية |
| DQ4 | حسابات مديونية خارج النطاق المعرَّف | مراجعة `EMPRCV_AccountScope` مع المالية |
| DQ5 | أرصدة قديمة > 3 سنوات بلا حركة | قائمة للمعالجة (شطب/متابعة قانونية) |
| DQ6 | حركات في فترات غير مقفلة | ملاحظة في التقرير + تنسيق مع الإقفال |
| DQ7 | موظفون منتهو الخدمة برصيد ≠ 0 | قائمة متابعة إلزامية للمالية |
