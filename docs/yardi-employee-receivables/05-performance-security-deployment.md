# 05 — الأداء والصلاحيات وخطة النشر

---

## 1. اعتبارات الأداء

### 1.1 التحدي

`gltrans` من أكبر جداول Voyager (عشرات إلى مئات الملايين من السطور في البيئات الكبيرة).
تقرير يقرأ كل الحركات التاريخية لآلاف الموظفين حتى تاريخ معيّن هو نمط استعلام ثقيل بطبيعته.

### 1.2 قيد أساسي: ممنوع تعديل جداول Yardi

في البيئات المستضافة لدى Yardi (Yardi Cloud) لا يُسمح عادةً بإضافة فهارس على الجداول
القياسية. لذلك **لا يعتمد التصميم على أي فهرس جديد على `gltrans`**، بل على الإستراتيجيات
التالية.

### 1.3 إستراتيجيات الأداء

| # | الإستراتيجية | الأثر |
| - | ------------ | ----- |
| P1 | **الفلترة المبكرة على الحسابات** — تقليص نطاق الحسابات قبل لمس الحركات (عادةً 5–20 حساباً من آلاف) | الأكبر أثراً؛ يقلّل الحركات المقروءة بأكثر من 95% |
| P2 | **جدول أرصدة مجمّع (Aggregate Cache)** `EMPRCV_LedgerCache` بمستوى (كيان، موظف، حساب، شهر) يُحدَّث ليلياً | R1 يقرأ آلاف الصفوف بدل ملايين |
| P3 | **تحديث تزايدي (Incremental)** بعلامة مائية على تاريخ الترحيل + إعادة بناء الأشهر المتأثرة بقيود بأثر رجعي | نافذة تحديث قصيرة |
| P4 | **الأرصدة الافتتاحية من الملخص الشهري** والحركات التفصيلية من `gltrans` للفترة المطلوبة فقط | R2 سريع حتى لتاريخ بعيد |
| P5 | **دوال النوافذ (Window Functions)** لحساب FIFO والرصيد المتحرك بلا مؤشرات أو حلقات | تنفيذ بمرور واحد |
| P6 | **`STRING_SPLIT` + جداول مؤقتة مفهرسة** للمعاملات متعددة الاختيار بدل `LIKE '%,x,%'` | خطط تنفيذ قابلة للبحث (SARGable) |
| P7 | **`OPTION (RECOMPILE)`** على الإجراءات ذات المعاملات المتغيّرة بشدة | تفادي مشكلة Parameter Sniffing |
| P8 | **عدم استخدام دوال على الأعمدة في شروط `WHERE`** (`PostDate <= @AsOf` لا `YEAR(PostDate)`) | الاستفادة من الفهارس القائمة |
| P9 | **`NOLOCK`/`READ COMMITTED SNAPSHOT` وفق سياسة العميل** لتفادي إعاقة معاملات Voyager | لا تأثير على المستخدمين التشغيليين |
| P10 | **تشغيل التقارير الثقيلة على نسخة قراءة (Reporting Replica)** إن توفّرت | عزل تام عن الإنتاج |
| P11 | **Snapshot لتقارير نهاية السنة** بدل استعلام حي | R3 لـ 1000 موظف من جدول واحد |
| P12 | **حد أقصى للصفوف + رسالة تضييق الفلاتر** | لا مهلات انتهاء (Timeouts) صامتة |
| P13 | **SSRS: تخزين مؤقت لمجموعات بيانات الفلاتر** (قوائم الكيانات/الحسابات) | زمن فتح الشاشة < 2 ثانية |
| P14 | **جدولة الدفعات الكبيرة (R3) خارج ساعات الذروة** عبر SSRS Subscriptions | لا ضغط على النظام نهاراً |

### 1.4 جدول التجميع المقترح

```
EMPRCV_LedgerCache
  EntityId, EmployeeKey, AccountId, CategoryCode, PeriodYear, PeriodMonth,
  DebitAmt, CreditAmt, NetAmt, TxnCount, LastPostDate,
  Seg1..Seg5, RefreshedOn
  PK/CLUSTERED INDEX: (EntityId, PeriodYear, PeriodMonth, EmployeeKey)
  INDEX: (EmployeeKey, EntityId) INCLUDE (NetAmt)
```

**قواعد الاتساق:** R1 يقرأ من الكاش فقط إذا كان `RefreshedOn` أحدث من آخر ترحيل مؤثر؛
وإلا يسقط تلقائياً إلى القراءة المباشرة (Fallback) مع إظهار ملاحظة "بيانات لحظية".
الكاش تحسين أداء لا مصدر حقيقة — ضابط المطابقة RC1 يُنفَّذ دائماً على المصدر.

### 1.5 أهداف وقياس

| التقرير | الهدف | الحمل المرجعي | طريقة القياس |
| ------- | ----- | ------------- | ------------ |
| R1 | ≤ 10 ث | 5,000 موظف × 3 سنوات × 8 كيانات | `EMPRCV_RunLog.DurationMs` (نسبة 95%) |
| R2 | ≤ 5 ث | موظف واحد × 5 سنوات | نفس المصدر |
| R3 دفعة | ≤ 5 دقائق | 1,000 نموذج PDF | زمن اشتراك SSRS |
| فتح شاشة الفلاتر | ≤ 2 ث | — | قياس يدوي في UAT |

`EMPRCV_RunLog` يجعل الأداء **مقاساً باستمرار** لا مفترضاً: أي تشغيل يتجاوز الهدف يظهر
في تقرير أداء أسبوعي.

## 2. الصلاحيات وأمن البيانات

### 2.1 مبدأ عام

بيانات مديونية الموظفين شديدة الحساسية (مالية + شخصية). المبدأ: **أقل صلاحية ممكنة**،
و**لا تسريب بالاستدلال** (المستخدم لا يعرف حتى وجود بيانات خارج نطاقه).

### 2.2 طبقات الأمان

| الطبقة | الآلية |
| ------ | ------ |
| L1 — الوصول للتقرير | صلاحية عنصر القائمة في Voyager (Menu/Function Security) لكل تقرير على حدة |
| L2 — نطاق الكيانات | `fn_UserEntityScope(@UserId)` يقاطع الكيانات المطلوبة مع المصرّح بها في أمان Voyager |
| L3 — أمان على مستوى الصف | تقييد بالقسم/الشريحة عبر `EMPRCV_UserScope` (مدير القسم يرى قسمه فقط) |
| L4 — أمان على مستوى العمود | إخفاء الحقول الحساسة (الهوية/الراتب) لغير المصرّح لهم عبر مجموعة صلاحيات |
| L5 — قاعدة البيانات | حساب خدمة SSRS بصلاحية `EXECUTE` على إجراءات `emprcv` فقط، بلا `SELECT` مباشر على أي جدول |
| L6 — التدقيق | `EMPRCV_RunLog` لكل تشغيل + `EMPRCV_ConfirmationLog` لكل إصدار نموذج |

> **إلزامي:** `@UserId` يُمرَّر من جلسة Voyager كمعامل **مخفي وغير قابل للتعديل** من قبل
> المستخدم. أي تصميم يسمح بتمرير `@UserId` يدوياً يعني تجاوزاً كاملاً لطبقة الأمان L2.

### 2.3 مصفوفة الصلاحيات

| الدور | R1 | R2 | R3 إصدار | R3L | إعداد النظام | نطاق البيانات |
| ----- | -- | -- | -------- | --- | ------------ | ------------- |
| CFO / مدير مالي | ✔ | ✔ | ✔ | ✔ | ✖ | كل الكيانات |
| مراقب مالي / محاسب | ✔ | ✔ | ✔ | ✔ | ✖ | كياناته |
| موارد بشرية | جزئي | ✔ | ✔ | ✔ | ✖ | كيانه + موظفوه |
| مدير قسم | ✔ | ✔ | ✖ | ✖ | ✖ | قسمه فقط |
| مدقق داخلي | ✔ | ✔ | ✖ | ✔ | ✖ | كل الكيانات (قراءة) |
| مدقق خارجي | ✔ | ✔ | ✖ | ✔ | ✖ | نطاق التدقيق، حساب مؤقت منتهي الصلاحية |
| مسؤول النظام | ✖ | ✖ | ✖ | ✖ | ✔ | إعداد فقط بلا أرصدة |

### 2.4 حماية البيانات الشخصية

| # | الضابط |
| - | ------ |
| S1 | إخفاء جزئي لرقم الهوية (`****1234`) في كل المخرجات |
| S2 | لا يعرض أي تقرير بيانات راتب — المديونية فقط |
| S3 | ملفات التصدير تحمل تصنيف "سري — للاستخدام الداخلي" في التذييل |
| S4 | حسابات المدقق الخارجي مؤقتة بتاريخ انتهاء وتُلغى بعد التدقيق |
| S5 | سجل التشغيل يحفظ من اطّلع على أي بيانات ومتى (≥ 7 سنوات) |
| S6 | نموذج R3 يحوي رصيد الموظف المعني فقط — لا قوائم جماعية عند التوزيع الفردي |
| S7 | مراجعة دورية (ربع سنوية) لقائمة المصرّح لهم |

## 3. خطة النشر (Deployment Plan)

### 3.1 البيئات

```
DEV (نسخة من الإنتاج، بيانات مقنّعة)  ──►  TEST/UAT (نسخة حديثة)  ──►  PROD
        بناء وتجربة                        اختبار المالية والتدقيق      تشغيل
```

كل انتقال يمرّ بطلب تغيير معتمد (Change Request) ونصوص نشر مرقّمة وقابلة للتراجع.

### 3.2 المراحل

| المرحلة | المخرجات | المدة التقديرية | البوابة |
| ------- | -------- | --------------- | ------- |
| M0 — التحقق من السكيما | `EMPRCV_SchemaMap` مكتمل + اختبار المطابقة مع تقرير Voyager قياسي | 3–5 أيام | **بوابة إلزامية: لا بناء قبلها** |
| M1 — الإعداد | جداول الإعداد + نطاق الحسابات + الفئات + الشرائح معتمدة من المالية | 3 أيام | اعتماد المالية على نطاق الحسابات |
| M2 — نواة البيانات | طبقة العزل + `vw_EmployeeLedger` + اختبارات المطابقة | 5 أيام | RC1 يمرّ على 3 تواريخ |
| M3 — R1 | الإجراء + RDL + الفلاتر + الأعمار + التصدير | 5 أيام | AT1، AT3، AT5، AT6 |
| M4 — R2 | الإجراء + RDL + الرصيد المتحرك + الدرل داون | 4 أيام | AT2، AT4 |
| M5 — R3 + R3L | اللقطة + النموذج + السجل + نص الإقرار المعتمد قانونياً | 5 أيام | AT7، AT8 |
| M6 — الأداء | جدول الكاش + الوظيفة الليلية + قياس الأهداف | 3 أيام | NF1–NF3 |
| M7 — الأمان | ربط الصلاحيات + اختبار بثلاثة أدوار | 2 أيام | AT5 |
| M8 — UAT | تنفيذ سيناريوهات القبول مع المالية والتدقيق | 5 أيام | توقيع قبول من المالية |
| M9 — التدريب والوثائق | دليل مستخدم + دليل تشغيل + جلسة تدريب | 2 أيام | — |
| M10 — الإطلاق والدعم المكثّف | النشر + متابعة أسبوعين | 10 أيام | استقرار بلا أعطال حرجة |

**الإجمالي التقديري: 7–8 أسابيع** (بافتراض توفر بيئة اختبار حديثة وتفرّغ مرجع من المالية).

### 3.3 ترتيب نصوص النشر

```
sql/00_config_tables.sql        -- الجداول وبياناتها الأولية
sql/10_source_views.sql         -- طبقة العزل (بعد اعتماد SchemaMap)
sql/20_core_views.sql           -- نواة البيانات
sql/30_usp_r1_summary.sql
sql/40_usp_r2_statement.sql
sql/50_usp_r3_confirmation.sql
sql/60_usp_recon_checks.sql     -- ضوابط المطابقة والفحوصات
sql/70_security_grants.sql      -- صلاحيات حساب SSRS
sql/80_cache_refresh_job.sql    -- الوظيفة الليلية (اختياري حسب الحجم)
rdl/EMPRCV_R1_Summary.rdl
rdl/EMPRCV_R2_Statement.rdl
rdl/EMPRCV_R3_Confirmation.rdl
rdl/EMPRCV_R3L_ControlLog.rdl
menu/register_voyager_menu_items.md   -- خطوات يدوية في Voyager
```

كل نص قابل لإعادة التنفيذ (idempotent)، ولكل نص نص تراجع مقابل في `sql/rollback/`.

### 3.4 خطة التراجع (Rollback)

| السيناريو | الإجراء | زمن الاسترداد |
| --------- | ------- | ------------- |
| خطأ في تقرير واحد | إخفاء عنصر القائمة + إعادة نشر RDL السابق | < 15 دقيقة |
| خطأ في إجراء مخزّن | تنفيذ نص التراجع للإصدار السابق | < 15 دقيقة |
| خطأ في الإعداد | استرجاع بيانات جدول الإعداد من النسخة الاحتياطية | < 30 دقيقة |
| فشل شامل | حذف سكيما `emprcv` بالكامل + إلغاء عناصر القائمة | < 1 ساعة |

> نظراً لأن الحل **للقراءة فقط ولا يعدّل أي بيانات Yardi**، فإن أسوأ سيناريو هو تعطّل
> التقارير — لا فقدان أو إفساد بيانات. هذه خاصية تصميمية مقصودة تقلّل مخاطر النشر جوهرياً.

### 3.5 التحقق بعد النشر (Post-Deployment Checklist)

| # | الفحص |
| - | ----- |
| 1 | تشغيل R1 لثلاثة كيانات وثلاثة تواريخ ومطابقة RC1 (فرق = 0) |
| 2 | تشغيل R2 لعشرة موظفين ومطابقة RC3 |
| 3 | اختبار الدرل داون على 5 أنواع مستندات |
| 4 | تصدير Excel و PDF والتحقق من التنسيق والعربية |
| 5 | اختبار بثلاثة مستخدمين بأدوار مختلفة (تأكيد حدود الصلاحيات) |
| 6 | التحقق من كتابة `EMPRCV_RunLog` لكل تشغيل |
| 7 | تشغيل تجريبي لـ R3 في وضع "مسوّدة" ومراجعة المالية |
| 8 | تشغيل الوظيفة الليلية ومراجعة زمنها وسجلها |
| 9 | التحقق من `#UNMAPPED = 0` |
| 10 | قياس الأداء الفعلي مقابل NF1–NF3 وتوثيقه |

### 3.6 التشغيل والصيانة (Run & Maintain)

| البند | التفصيل |
| ----- | ------- |
| المراقبة | تنبيه عند: فشل الوظيفة الليلية، ظهور `#UNMAPPED`، انحراف RC1، تجاوز أهداف الأداء |
| الدورة الشهرية | مراجعة تقرير الاستثناءات + مراجعة سجل التشغيل |
| الدورة السنوية | تجميد لقطة نهاية السنة → إصدار R3 → متابعة R3L → تسليم المدقق |
| إدارة التغيير | إضافة حساب/فئة/شريحة = إدخال بيانات في جداول الإعداد (بلا نشر برمجي) |
| الترقيات | بعد كل ترقية Voyager: إعادة تنفيذ اختبار طبقة العزل (مقارنة مع تقرير قياسي) قبل الاعتماد |
| الملكية | مالك وظيفي: المالية · مالك تقني: فريق تطبيقات Yardi |

### 3.7 التوسعات المستقبلية (مصمَّم لها، غير منفَّذة)

| # | التوسعة | الأثر على التصميم الحالي |
| - | ------- | ------------------------ |
| E1 | مديونية الموردين/المقاولين بنفس النمط | إضافة نوع بُعد جديد — النواة كما هي |
| E2 | لوحة مؤشرات إدارية (Dashboard) | تقرأ من نفس `vw_EmployeeLedger` |
| E3 | إرسال المصادقات بالبريد وتتبّع الرد | إضافة اشتراك SSRS + تحديث `ConfirmationLog` |
| E4 | التوقيع الإلكتروني | حقل مرجع توقيع في `ConfirmationLog` |
| E5 | جداول سداد وتنبيهات تأخر | جدول خطط سداد جديد يرتبط بـ `EmployeeKey` |
| E6 | مخصص ديون مشكوك في تحصيلها | قاعدة تعتمد على شرائح الأعمار الموجودة |

كل التوسعات أعلاه تُبنى فوق النواة دون تعديلها — وهو المعيار العملي لكون التصميم
معيارياً وقابلاً للتوسع.
