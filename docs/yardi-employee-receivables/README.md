# حزمة تقارير مديونية الموظفين — Yardi Voyager

> **Employee Receivables Reporting Package**
> ثلاثة تقارير مترابطة لمتابعة مديونية الموظف وتلبية متطلبات التدقيق المالي،
> مبنية على معاملات الحسابات العامة (GL) مع دعم السيجمنتيشن وتعدد الشركات والكيانات.

---

## 1. نطاق الحزمة (Scope)

| # | التقرير | الرمز | الجمهور | الغرض |
| - | ------- | ----- | ------- | ----- |
| R1 | ملخص مديونية الموظفين | `EMPRCV-R1` | الإدارة المالية / الإدارة العليا | نظرة إجمالية بالأرصدة والأعمار حتى تاريخ معيّن |
| R2 | كشف حساب تفصيلي للموظف | `EMPRCV-R2` | المالية / الموارد البشرية | حركة تفصيلية برصيد متحرك وخيار درل داون للمستند |
| R3 | نموذج اعتماد رصيد الموظف | `EMPRCV-R3` | التدقيق / المالية / الموظف | إقرار وتوقيع بالرصيد في نهاية السنة المالية |

الترابط بين التقارير:

```
R1  ملخص المديونية
 │   (Drill-down: الموظف + تاريخ الرصيد + الكيان)
 ▼
R2  كشف الحساب التفصيلي  ──►  Drill-through إلى شاشة المستند في Voyager
 │   (Generate: نهاية السنة المالية)
 ▼
R3  نموذج اعتماد الرصيد  ──►  سجل متابعة النماذج (Confirmation Control Log)
```

## 3. المبادئ التصميمية (Design Principles)

1. **معياري (Modular):** كل تقرير طبقة مستقلة فوق نواة بيانات واحدة (`vw_EmployeeLedger`).
   إضافة تقرير رابع لا تتطلب تعديل الثلاثة الحالية.
2. **قابل للتوسع (Extensible):** تعريف الموظف، نطاق الحسابات، فئات المديونية، وشرائح
   السيجمنتيشن كلها **مقودة بالإعداد (config-driven)** في جداول، لا في كود التقارير.
3. **آمن عند الترقية (Upgrade-safe):** لا تعديل على أي كائن قياسي من Yardi. جميع الكائنات
   المخصّصة تحمل البادئة `EMPRCV_` داخل سكيما `emprcv` مخصّصة.
4. **طبقة عزل واحدة (Anti-Corruption Layer):** الكائنات التي تلمس جداول Yardi الفعلية
   محصورة في ملف واحد (`sql/10_source_views.sql`). أي فرق في السكيما بين إصدارات Voyager
   يُعالج في مكان واحد فقط.
5. **قابل للتدقيق (Auditable):** لقطة أرصدة مجمّدة لنهاية السنة، سجل تشغيل التقارير،
   سجل متابعة نماذج الاعتماد، وضابط مطابقة إلزامي مع ميزان المراجعة.

## 4. تحذير مهم قبل البناء — التحقق من السكيما (Schema Validation)

أسماء جداول وأعمدة Yardi Voyager تختلف حسب:

- إصدار Voyager (7S مقابل 8) وحزمة الـ Service Pack.
- طريقة تفعيل السيجمنتيشن لدى العميل (عدد الشرائح ومصدرها).
- الوحدات المفعّلة (HR / Payroll / Payables) وطريقة تمثيل الموظف.

لذلك **يجب** تنفيذ قائمة التحقق التالية في بيئة الاختبار قبل بدء البناء، وتثبيت النتائج في
جدول الإعداد `emprcv.EMPRCV_SchemaMap`:

| # | العنصر المطلوب تأكيده | الاستعلام المقترح |
| - | -------------------- | ----------------- |
| 1 | جدول حركات الأستاذ العام واسم عمود المبلغ | `SELECT TOP 1 * FROM gltrans` |
| 2 | جدول رؤوس القيود ونوع/حالة المستند | `SELECT TOP 1 * FROM header` |
| 3 | شجرة/دليل الحسابات وطريقة ترميزه | `SELECT TOP 1 * FROM account` |
| 4 | تمثيل الكيان/الشركة (Property / Entity / Owner) | `SELECT TOP 1 * FROM property` |
| 5 | مصدر شرائح السيجمنتيشن (جدول مستقل أم ترميز داخل رقم الحساب) | مراجعة إعداد Chart of Accounts |
| 6 | تمثيل الموظف (Vendor / Employee / Segment / Sub-account) | ورشة عمل مع المالية والموارد البشرية |
| 7 | جداول أمان المستخدم ونطاق الكيانات المسموح بها | مراجعة إعداد Voyager Security |
| 8 | جدول الدفاتر (Books) وتحديد دفتر التقرير (Accrual) | `SELECT * FROM book` |

> نتيجة هذه القائمة هي المدخل الوحيد لملف `sql/10_source_views.sql`.
> لا يُبنى أي تقرير قبل اعتمادها من فريق Yardi لدى العميل.

## 5. الافتراضات (Assumptions)

| # | الافتراض | الأثر إن لم يتحقق |
| - | -------- | ----------------- |
| A1 | مديونية الموظف مسجّلة في حسابات GL محددة يمكن حصرها | يلزم تحليل إضافي لتحديد مصدر المديونية |
| A2 | يمكن تمييز الموظف داخل الحركة عبر أحد المصادر الأربعة المدعومة | يلزم إضافة مصدر جديد في `EMPRCV_EmployeeSource` |
| A3 | جميع الحركات مرحّلة (Posted) قبل ظهورها في التقرير | تُستثنى الحركات غير المرحّلة صراحةً |
| A4 | العملة موحّدة داخل الكيان الواحد | يُفعّل وضع "تقرير لكل عملة" أو التحويل بسعر تاريخ الرصيد |
| A5 | إمكانية إنشاء كائنات مخصّصة في قاعدة البيانات (أو قاعدة تقارير منفصلة) | يُنشر الحل كاستعلامات داخل RDL بدل الإجراءات المخزّنة (أداء أقل) |

الإنتاج بعد؛ نصوص SQL المرفقة مرجعية وتحتاج تمرير مرحلة التحقق من السكيما (القسم 4).
